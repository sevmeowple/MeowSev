# 调试与业务编写经验指导

> 基于 `profile compact` 问题排查、Satori 消息推送方案落地的实战经验提炼。
> 这份文档不关心具体业务逻辑，只记录"如何高效地解决一个不知道原因的问题"。

---

## 一、接到问题后：先对齐信息，再动手

### 1.1 用户描述 ≠ 真实问题

用户说 "compact 返回太快了"，实际根因是 **timestamp 毫秒级 vs 查询秒级**。用户感知到的是症状，不是病因。

**正确做法：**
1. 先复现（让用户再跑一次，看日志输出）
2. 对比用户描述和系统实际行为（"你说无消息，但数据库里有 5677 条"）
3. 用数据说话，不要靠猜

### 1.2 信息同步的节奏

| 时机 | 应该做什么 | 反面例子 |
|------|-----------|---------|
| 刚接到问题 | 确认复现步骤 + 查看日志 | 直接开始改代码 |
| 找到假设 | 先和用户说"我怀疑是 X，正在验证" | 埋头调试半小时不说话 |
| 验证失败 | 立刻反馈"X 不对，现在怀疑 Y" | 死磕一个错误方向 |
| 找到根因 | 解释原因 + 给出修复方案 | 直接发 PR 让用户自己看 |
| 修复后 | 验证结果 + 确认是否解决 | "应该好了吧" |

**关键原则：每做完一个验证步骤，就给用户一个更新。** 哪怕只是 "正在查"，也比沉默好。

## 二、定位问题：日志 → 测试 → 代码

### 2.1 日志是第一信息源

`compact` 问题的排查顺序：

```
用户报告 "返回太快"
    ↓
查看日志："无消息，跳过"
    ↓
日志里有时间戳范围（1776614400 ~ 1776700799）
    ↓
写脚本查数据库 → 发现 timestamp 是毫秒级
    ↓
根因：代码查询用了秒级
```

**如果没先看日志**，可能会去怀疑：
- MessageFilter 过滤太严格
- is_processed 字段问题
- LLM 超时逻辑

这些都是无关方向，浪费大量时间。

### 2.2 写测试脚本验证假设

发现 `timestamp` 可疑时，立刻写脚本验证：

```bash
# 不要靠脑子算，直接跑 SQL
sqlite3 data.sqlite "SELECT COUNT(*) FROM messages WHERE timestamp >= 1776614400"
# → 0 条（秒级查询）

sqlite3 data.sqlite "SELECT COUNT(*) FROM messages WHERE timestamp >= 1776614400000"
# → 5677 条（毫秒级查询）
```

**测试脚本的价值：**
- 消除猜测，5 分钟确定方向
- 可以复用给用户看，证明根因
- 修复后可以再跑一遍，确认解决

### 2.3 代码审查放在最后

不要一上来就通读代码。先通过日志和测试缩小范围，再精读相关代码。

这次问题的代码审查范围：
- ❌ 一开始通读 `ProfileWorker.ts`（300+ 行）
- ✅ 先看 `ProfileScheduler.ts` 的查询逻辑（10 行）
- ✅ 确认根因后，grep 所有用到 `timestamp` 的地方，批量修复

## 三、WebSearch：不要泛泛而搜

### 3.1 搜索策略：从具体到抽象

这次 Koishi 路由问题的搜索演变：

| 搜索尝试 | 结果 | 评价 |
|---------|------|------|
| `Koishi ctx.router POST route console plugin 405` | 一堆 koa-router 通用问题 | 太泛，没解决 |
| `Koishi 消息推送 HTTP API 主动发消息` | 找到 server-satori 官方文档 | ✅ 精准命中 |
| `Satori protocol API message.create send private message` | 找到 API 格式和私聊频道 ID 格式 | ✅ 解决最后一公里 |

**教训：**
- 第一轮搜索用词太技术化（`ctx.router`），陷在底层框架细节里
- 第二轮换成业务视角（"消息推送"），立刻找到官方方案
- 第三轮用协议名（`Satori protocol`）+ 具体操作（`message.create`），找到具体 API 参数

### 3.2 什么时候该搜索

| 场景 | 建议 |
|------|------|
| 熟悉业务代码的 bug | 先看日志和代码，不用搜 |
| 框架/库的用法不确定 | 直接搜官方文档 |
| 报错信息很陌生 | 搜报错 + 框架名 |
| 需要设计架构方案 | 搜最佳实践 + 技术栈名 |
| 试了 3 次还没解决 | **立刻停手去搜文档**，不要硬试 |

### 3.3 搜索后的验证

搜到 `server-satori` 方案后，**立刻验证**：
1. 检查本地是否已安装（`ls node_modules/@koishijs/plugin-server-satori`）
2. 启用后 curl 测试 API
3. 确认私聊格式（`private:USER_ID`）

**不要看完文档就以为懂了**，必须实际调通一次。

## 四、方案设计：给用户选择权

### 4.1 多方案对比表

这次消息推送有两个方案：

| 方案 | 改动量 | 可靠性 | 维护成本 |
|------|--------|--------|----------|
| A: NapCat 开 HTTP Server | 改 1 行配置 | 高（原生 OneBot） | 低 |
| B: Koishi server-satori 代理 | 改 koishi.yml + utils/message.ts | 中（依赖 Satori 协议） | 中 |

用户选了 B，因为"Server 端代码不用大改"是用户关心的点。

### 4.2 方案选择时的沟通原则

- **先说清楚各方案的优缺点**，不要替用户做决定
- **说明推荐方案及理由**
- **确认用户对改动的接受度**（"需要改 Koishi 配置，可以吗？"）

## 五、避免陷阱：这次踩过的坑

### 5.1 "应该可以" → 必须验证

一开始以为 `send_private_msg` OneBot API 可以直接用，没验证 NapCat 配置。结果 `httpServers: []`，根本没人监听 3033 端口。

**原则：任何外部依赖，使用前先验证可用性。**

### 5.2 盲目试错框架行为

在 `con-to-server` 插件里试了：
- `ctx.router.post('/send-msg')` → 405
- `ctx.server.use(middleware)` → 405
- `ctx.router.post('/api/send-msg')` → 405

试了 3 种方式都失败，浪费大量时间。

**正确做法：** 第一次 405 后就应该停手，去搜"Koishi 如何暴露 HTTP API 给外部调用"，而不是硬试路由注册方式。

### 5.3 忽略编译后的产物

改了 `src/index.ts` 后忘记重新编译，`lib/index.js` 还是旧代码，导致改动不生效。

**原则：改 TypeScript 源码后，必须确认编译产物已更新。**

## 六、快速检查清单

接到一个 bug 报告时，按这个顺序来：

```
□ 复现问题（让用户操作或自己触发）
□ 查看日志，找到错误信息或异常行为
□ 写脚本验证最关键的假设（通常涉及数据或配置）
□ 缩小代码范围，定位具体文件/函数
□ 如果是框架/库的问题，先搜索文档而不是硬试
□ 找到根因后，检查是否有其他同类问题
□ 给出修复方案，让用户确认
□ 修复后验证，同步结果
```

## 七、这次事件的时间线复盘

| 时间 | 事件 | 做对/做错 |
|------|------|----------|
| T+0 | 用户报告 compact 返回太快 | ✅ 先查日志 |
| T+5min | 写脚本验证 timestamp | ✅ 快速定位 |
| T+10min | 修复秒级→毫秒级 | ✅ 批量修复所有相关文件 |

| T+20min | 修复 daily_digests 逻辑 | ✅ 用 SELECT/UPDATE/INSERT 替代 |
| T+25min | 提出 is_processed + 并发优化 | ✅ 给用户选择权 |

| T+40min | 用户要求加私聊推送 | ✅ 先检查现有能力 |
| T+45min | 发现 NapCat HTTP 未开启 | ✅ 提出方案A/B |
| T+50min | 用户选B，开始实施 | ⚠️ 没先搜文档，直接硬试路由 |
| T+70min | 试了3种路由方式都405 | ❌ 应该早停手去搜 |
